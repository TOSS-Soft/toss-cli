# TOSS CLI v2.1.1 Issue #86 Validator Cold-Start Design

**Status:** Approved for implementation planning

**Date:** 2026-08-20

**Issue:** [#86](https://github.com/TOSS-Soft/toss-cli/issues/86)

**Epic:** [#83](https://github.com/TOSS-Soft/toss-cli/issues/83)

**Base:** `agent/issue-85-explicit-test-lanes` at `2caf811`

## 1. Purpose

Reduce validator cold-start and repeated CLI composition cost without changing
the public CLI, contract, schema, error, authority, state-machine, or
durability surface. The implementation loads only the requested schema's exact
external dependency closure, compiles each validator once per validator
runtime, and retains a process-global default runtime.

Command semantics remain covered in process through the public parser and
dispatcher with the existing memory store. A minimum representative real-binary
set continues to prove operating-system process boundaries. No assertion is
deleted merely because a subprocess is removed.

## 2. Binding Constraints

- Preserve the exact synchronous exports and call shape of
  `src/contracts/validator.js`: `createContractValidator()` and
  `validateDocument(value, schemaId)`.
- Preserve canonical JSON rejection, closed-schema behavior, formats,
  references, unknown-schema handling, normalized Ajv errors, and validation
  ordering.
- Do not add a validation bypass, test-only production switch, network access,
  generated validator build step, or public CLI option.
- Keep the default validator process-global and keep Ajv, the schema registry,
  dependency state, and compiled functions unreachable by callers.
- Keep every command-specific assertion represented by an in-process owner
  before reducing a real-binary case.
- Keep representative real-binary checks for argument parsing, JSON and human
  output, exit codes, project/cwd isolation, environment isolation, and zero
  forbidden network access.
- Ordinary correctness tests cannot contain timing thresholds. Performance
  acceptance uses an opt-in three-run benchmark on the reference runner.
- Do not modify `package-lock.json` or
  `docs/performance/v2.1.1-baseline.json`.
- Keep manifest concurrency at `1`; issue #87 remains the only authority for
  selecting a different checked-in concurrency.

## 3. Measured Starting Evidence

All measurements below were captured from clean commit `2caf811` on the named
macOS/Node.js 26.6.0 reference host. They are design evidence, not ordinary
test assertions.

### 3.1 Focused gate CLI baseline

`node --test test/gate-cli-round1.test.js` produced three successful samples:

| Run | Wall time |
| --- | ---: |
| 1 | 32581.990 ms |
| 2 | 32685.561 ms |
| 3 | 32656.405 ms |

The locked same-runner median for issue #86 is `32656.405 ms`. A material
focused improvement means a final median no greater than `22859.484 ms`, a
30 percent reduction. The final report retains all three before and after
samples.

### 3.2 Process, module, and validator observations

- Empty Node process median: `22.694 ms` across five runs.
- Minimal unimplemented CLI path median: `37.911 ms` across five runs.
- Current validator-module import median: `35.477 ms` across three fresh
  processes.
- Current first `command-result.v1` validation median after import:
  `3.256 ms`.
- Real `architecture review` process median: `4116.310 ms`.
- The same disk-backed command in process median: `3931.188 ms`.
- The same public dispatcher command with the existing memory store median:
  `6.142 ms`.

The data rejects a process-only explanation. Removing a process saves about
`185 ms` for this command, while replacing repeated disk-backed catalog
composition with the existing in-memory semantic boundary removes nearly four
seconds. Real disk behavior remains covered by its existing integration and
durability owners and by representative real-binary sentinels.

## 4. Alternatives and Decision

### 4.1 Selected: demand-driven dependency closure

Keep a closed frozen metadata catalog of logical schema IDs, canonical `$id`
URIs, and repository-relative files. On first request, read that root schema,
walk external `$ref` URIs, load the exact transitive closure, register only
that closure, compile the requested validator, and cache it. Subsequent calls
reuse the compiled function. The default runtime is created at module load but
performs no schema I/O or Ajv construction until its first validation.

This is selected because it satisfies the unused-family criterion, preserves
the synchronous API, avoids generated artifacts, and matches the observed
1--4-file closures.

### 4.2 Rejected: test refactor with the eager validator unchanged

Moving redundant command cases in process supplies the largest focused-suite
gain, but leaving the validator eager would still read and register unrelated
families. This fails issue #86's explicit unused-family acceptance criterion.

### 4.3 Measured but rejected by default: standalone generated validators

Standalone validators are retained as a benchmark alternative only. They can
be selected only if all of the following are true:

1. their final focused-suite median is at least 10 percent lower than the
   demand-driven candidate;
2. generated output is deterministic and verified against every source schema;
3. package and source-drift checks fail closed; and
4. normalized valid, invalid, and error outputs are byte-equivalent.

The provisional measurement predicts that validator microseconds will not
remove another 10 percent from a suite dominated by command composition. If
the formal measurement confirms that prediction, standalone output is not
checked in and no generation step is added.

### 4.4 Rejected: command-global verified catalog cache

Caching a verified artifact catalog across production CLI commands would mix
command lifetimes and could weaken stale-state, mutation, or durability
boundaries. Issue #86 changes test composition, not production artifact-store
trust. Each real command continues to construct and verify its production
catalog exactly as before.

## 5. Architecture

### 5.1 Closed schema metadata

Create `src/contracts/schema-catalog.js` as the only mapping authority. Each
frozen row contains exactly:

```js
{
  schemaId: "command-result.v1",
  uri: "https://toss.software/schemas/pipeline/command-result.v1.schema.json",
  relativePath: "../../contracts/pipeline/command-result.v1.schema.json",
}
```

The catalog is ASCII-sorted and unique by `schemaId`, `uri`, and path. Rows,
the row array, and lookup results are immutable. Catalog validation rejects
unknown fields, duplicate identities, unsafe paths, unsupported URI schemes,
accessors, symbols, and non-enumerable data before any schema file is read.

### 5.2 Dependency-aware validator runtime

Create `src/contracts/validator-runtime.js` with one internal construction
boundary:

```js
createValidatorRuntime({catalog, readSchema, createAjv, observe})
```

Production passes the closed catalog and private real dependencies. Focused
tests pass counted or failing dependencies. This internal function returns
only a frozen `{validateDocument}` object; it never returns its registry, Ajv
instance, loaded schemas, dependency graph, or compiled validators.

`validateDocument(value, schemaId)` follows this exact order:

1. resolve the logical schema ID or throw the existing
   `Unknown contract schema: <id>` error;
2. return the cached compiled validator when present;
3. read and parse the requested schema;
4. verify its exact expected `$id`;
5. recursively inspect own JSON data for external `$ref` URIs, discarding only
   their fragment for catalog lookup;
6. load every dependency once with cycle-safe visitation;
7. fail closed on an unresolved URI, malformed JSON, unsafe JSON value,
   unexpected `$id`, invalid schema, or compile error;
8. create the private Ajv instance on first use, install the unchanged strict
   options and `rfc3339-date-time` format, and register the closure;
9. compile and cache only the requested validator;
10. canonicalize the input document and return the unchanged normalized
    result.

The runtime does not cache a failed compile as success. A later call cannot
observe partial state through a public object. Production catalog validity
means compile failures indicate repository corruption and remain fail closed.

### 5.3 Synchronous lazy Ajv boundary

`src/contracts/validator.js` stops importing Ajv at module evaluation. A
private `createRequire(import.meta.url)` loader obtains `ajv/dist/2020.js`
synchronously only when the runtime first requires an Ajv instance. This keeps
`validateDocument` synchronous and preserves Node.js `>=20` support.

`createContractValidator()` constructs an independent lazy runtime with the
same behavior as before. The module-level default constructs one lazy runtime
and every exported `validateDocument` call reuses it.

### 5.4 Phase observation and benchmark

Observation is dependency-injected only into the internal runtime. It is not
an environment switch or a public validator option. The observer receives
closed phase events for:

- schema I/O;
- dependency discovery;
- Ajv creation and schema registration;
- requested-validator compilation; and
- first validation.

Create an opt-in benchmark under `scripts/performance/` that runs exactly three
fresh-process samples for eager reference, demand-driven runtime, and
standalone experiment. It also records empty-process overhead, CLI module
loading, representative command execution, and total wall time. Correctness
tests inject a clock and fixtures; they assert report shape and arithmetic, not
real durations.

The report version is `toss-validator-cold-start-report.v1`. It contains a
closed identity copied from the #84 protocol, the exact strategy name, three
successful samples, phase medians derived from those samples, focused gate CLI
before/after samples, and a decision section naming the selected and rejected
alternatives. Ordinary runs write to stdout or an ignored `.superpowers/`
path. They never update the #84 baseline.

The measured decision is summarized in
`docs/performance/v2.1.1-validator-decision.md`, including why standalone and
eager alternatives were rejected.

### 5.5 Command-semantic and real-binary boundaries

The ten original issue-28 command rows remain represented in a checked-in
matrix. Their parser, exit-code, and non-`COMMAND_CONTEXT_INVALID` assertions
run in process through `parseCommand` and `dispatchCommand`, using the existing
`memoryCommandStore` and exact per-command services. Existing focused gate
tests remain the authority for detailed decision, approval, audit, readiness,
publication, and writer semantics.

`test/gate-cli-round1.test.js` retains two representative production-binary
sentinels against a prepared real artifact store:

1. a JSON `architecture review` success, proving executable parsing, exact
   envelope, stdout/stderr separation, exit `0`, and explicit project-root
   selection; and
2. a human `decisions list` blocked result, proving human rendering,
   stdout/stderr separation, stable exit `4`, and the same project isolation.

Both processes start from a cwd distinct from the project root and load a
test-only network guard before the production executable. The guard makes
`fetch`, HTTP(S), TCP, TLS, and DNS connection attempts fail with a stable
sentinel. It does not reject harmless module imports; it rejects actual network
use. This provides stronger evidence than scanning stderr for provider names.

The package executable remains independently covered by the package lane.
Argument usage failures, JSON error envelopes, help/version routing, and
environment behavior remain independently covered by `test/cli-contract.test.js`.

## 6. Validation Equivalence

Add a test-only eager reference validator fixed to the issue #86 base behavior.
For every catalog schema, compare demand-driven and eager results for a
canonical invalid object. Compare representative valid and invalid fixtures
from common, agent, pipeline, and design families. Compare canonical-JSON
failures, format failures, additional-property failures, reference failures,
unknown logical IDs, and normalized error arrays with `deepStrictEqual`.

The full existing suite remains the valid-fixture oracle for all production
builders. A new test cannot weaken or replace those tests.

Counted runtime tests prove:

- no schema is read and Ajv is not created at runtime construction;
- `command-result.v1` reads and registers only itself;
- a four-file root reads each dependency exactly once;
- a second validation of the same root performs no I/O, registration, or
  compilation;
- a second root reuses already loaded dependencies;
- returned results and errors cannot mutate the runtime; and
- malformed catalogs, unresolved dependencies, schema-ID drift, invalid
  definitions, and compile failures fail closed.

## 8. Acceptance and Verification

Issue #86 is ready only when all of the following are true:

1. the formal three-run report attributes process, module, schema I/O,
   registration, compilation, first validation, command, and total time;
2. the report names demand-driven, eager, and standalone alternatives and
   records the selected design;
3. unused schema families are not read, registered, or compiled;
4. per-runtime compiled validators are reused and private;
5. eager-reference and demand-driven normalized results are equivalent;
6. the ten-row in-process matrix and the two guarded real-binary sentinels pass;
7. the focused gate CLI median is at most `22859.484 ms` and all three final
   samples exit `0`;
8. `node ./scripts/test-manifest.mjs`, every public lane, `npm test`, and
   `npm pack --dry-run` pass;
9. an issue-specific fast and full three-run capture is recorded without
   relaxing `15000` or `90103`;
10. `package-lock.json` and the tracked performance baseline are byte-identical
    to `2caf811`; and
11. independent review finds no Critical or Important issue.

The full-suite budget can remain above `90103 ms` until #87 and #88 only if the
measured #86 delta is retained, the limit is not relaxed, and the miss is
reported explicitly.
