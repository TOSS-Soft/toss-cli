# TOSS CLI v2.1.1 Issue #87 Durable-Store and Concurrency Design

**Status:** Approved for implementation planning

**Date:** 2026-08-21

**Issue:** [#87](https://github.com/TOSS-Soft/toss-cli/issues/87)

**Epic:** [#83](https://github.com/TOSS-Soft/toss-cli/issues/83)

**Base:** `agent/issue-86-validator-cold-start` at `46c46b0`

## 1. Purpose

Reduce durable-filesystem amplification in command-semantic tests and select
the full-suite concurrency from measured candidates `1`, `2`, `3`, and `4`.
Pure command and state semantics use the existing in-memory store pattern.
Persistence, durability, atomicity, recovery, filesystem safety, and real CLI
claims continue to execute against production boundaries.

Issue #87 is complete only when the canonical full-suite three-run median is
at most the unchanged `90103 ms` budget. A miss remains owned by #87; it is not
deferred to #88. The implementation may not meet the target by deleting
coverage, weakening production guarantees, relaxing the budget, or hiding a
failed sample.

## 2. Binding Constraints

- Preserve every public command, option, output envelope, exit code, contract,
  schema, authority rule, state-machine transition, persistence behavior, and
  recovery behavior.
- Do not add a production flag, environment variable, or alternate code path
  that disables validation, `fsync`, atomic replacement, lineage, locking,
  symlink defense, interruption handling, or recovery.
- Keep real production-store coverage for atomic append, immutable revision
  bytes, monotonic revision, exact parent lineage, content hashes, exact
  reference verification, path containment, symlink rejection, concurrent
  writers, interruption, resume, recovery, and packed-artifact execution.
- Every semantic test moved from a real store must name the retained real-store
  guarantee owners that replace its incidental filesystem coverage.
- Keep real CLI and runtime tests for operating-system process properties.
  Process-boundary assertions cannot be replaced by in-process simulations.
- Use isolated temporary roots with deterministic cleanup for every real-store
  test. Concurrent tests cannot share, inspect, overwrite, or clean another
  test's state.
- Measure only explicit concurrency values `1` through `4`. Do not derive the
  default from ambient CPU count or accept an unbounded value.
- Keep result emission in manifest order and preserve exact child output,
  status, signal, and owning entry at every concurrency.
- Keep ordinary correctness tests free of wall-clock thresholds. Performance
  acceptance uses opt-in three-run reports on the reference runner.
- Do not modify `package-lock.json` or relax
  `docs/performance/v2.1.1-baseline.json`.
- Keep #87 open and in progress unless every acceptance condition in section 9
  passes, including the `90103 ms` canonical full budget.

## 4. Alternatives and Decision

### 4.1 Selected: boundary inventory, targeted semantic migration, then measured concurrency

First record a closed ownership inventory for semantic, store-integration,
durability/atomicity, real-CLI, package, and release claims. Move only the
high-cost pure command semantics to the shared memory store. Retain or split
out explicit production-store counterparts. After the semantic/store boundary
is clean, measure concurrency `1`, `2`, `3`, and `4`, then check in the stable
candidate with the lowest three-run wall-time median.

This approach is selected because it attacks the measured disk amplification
without treating the in-memory fixture as a durability oracle. It also makes
the concurrency decision attributable and reversible.

### 4.2 Rejected: concurrency-only optimization

Changing only the scheduler has a smaller diff but leaves individual owners at
roughly 84, 39, 39, and 27 seconds. Contention can increase system CPU and
process cost, and one 84-second owner leaves almost no budget for runner and
package overhead. This approach is not credible against `90103 ms` and does
not satisfy the issue's durable-store classification requirement.

### 4.3 Rejected: broad in-memory conversion

Replacing every production store with memory could make the suite faster but
would erase the evidence that immutable bytes, locks, path checks, atomic
renames, interruption, and recovery work on a real filesystem. It creates a
large review surface and invites semantic drift. Only claims explicitly
classified as semantic may move.

## 5. Architecture

### 5.1 Closed boundary inventory

Add a versioned JSON inventory under `scripts/` and a small validator module.
The inventory has two closed, ASCII-sorted collections:

1. **Guarantees** name one stable guarantee ID, one classification, and one
   primary executable owner. Classifications are exactly `semantic`,
   `store-integration`, `durability-atomicity`, `real-cli`, `package`, and
   `release`.
2. **Semantic delegations** name each executable entry that uses the memory
   store and the real guarantee IDs that retain its former incidental
   production-store coverage.

Paths are canonical repository-relative manifest entries. Guarantee IDs and
semantic entries are unique, and every guarantee resolves to exactly one
primary manifest owner in a compatible lane. One entry may be the primary
owner for multiple distinct guarantees. Every referenced real guarantee
exists and has a non-semantic classification. Imported support and fixture
files cannot be owners. Unknown fields, missing delegations, duplicate
identities, unsafe paths, unsorted rows, unknown manifest entries, and
classification/lane mismatches fail before tests execute.

One focused correctness owner validates the inventory and the mapping between
it and `scripts/test-manifest.json`. This is the permanent proof that a moved
semantic test did not silently delete its production boundary.

### 5.2 In-memory semantic store

Keep `test/support/command-fixture.js` as the single in-memory command-store
authority. Strengthen only the behavior required by public command semantics:

- immutable append results and defensive copies;
- monotonic revisions and exact parent relationships;
- deterministic list ordering;
- exact-reference verification; and
- closed failures for missing or conflicting artifacts.

The fixture remains test-only. It does not implement or claim `fsync`, file
locking, atomic rename, symlink defense, interruption cleanup, or recovery.
Focused parity tests compare its semantic results with a production store for
the shared public operations, while real-boundary owners remain authoritative
for filesystem guarantees.

### 5.3 Targeted command-test migration

Classify every subtest in the high-cost design, project, and feature command
owners before changing its store. Pure parser, dispatcher, orchestration,
decision, idempotency-as-command-result, and state-transition assertions use
the memory store. Assertions about persisted bytes, verified restart state,
append interruption, partial operations, or recovery continue to use the
production store.

When one file mixes both classes, split it at the ownership boundary: the
semantic entry belongs to the fast lane and the real-store counterpart belongs
to integration or end-to-end. The split cannot change assertion meaning or
duplicate an executable entry. `test/design-cli-runtime.test.js` and the two
production sentinels in `test/gate-cli-round1.test.js` remain real process
owners; they are not converted merely because they are slow.

Production files under `src/` are not expected to change. If migration exposes
a product correctness defect, implementation stops for a design revision
instead of disguising the defect in a fixture.

### 5.4 Real-store and isolation owners

The boundary inventory names primary production owners for at least:

- immutable atomic append and monotonic revision;
- exact hash, reference, and parent-lineage verification;
- containment and symbolic-link rejection;
- append locks and concurrent writers;
- failed or interrupted temporary-file cleanup;
- resumable workflows and recovery from partial operations;
- idempotent reruns against persisted state; and
- execution from the packed production artifact.

All real-store helpers create a unique temporary root for each test and remove
only that root through test cleanup. A dedicated integration owner runs
repeated and concurrent fixtures with identical logical artifact IDs, proves
their physical roots differ, proves no cross-root reads or cleanup, and checks
that no temporary artifacts remain after success or injected failure.

### 5.5 Concurrency measurement harness

Add an opt-in performance worker under `scripts/performance/`. It loads and
validates the checked-in manifest, replaces only the in-memory concurrency
field with one candidate from `1` through `4`, and invokes the same exported
lane scheduler used by `npm test`. It does not change the public runner CLI,
write a temporary manifest, or expose a production environment override. The
worker and report model are import-only support files and cannot become test
manifest entries.

The benchmark runs candidates serially in ascending order. Each candidate gets
exactly three fresh-process full-suite samples with already installed
dependencies. The closed report records, for every sample:

- candidate concurrency and exact entry inventory;
- commit, Node.js version, platform, architecture, and lock digest;
- wall, user CPU, and system CPU time;
- exit status, signal, peak fresh-process count, and orphan-process evidence;
- duplicate, missing, and out-of-order result evidence; and
- temporary-root leak and isolation findings.

A candidate is stable only when all three samples pass, every manifest entry
runs exactly once, result emission remains in manifest order, no orphan or
temporary state remains, and the repeated/concurrent isolation owner passes.
Among stable candidates, the exact lowest wall-time median wins. An exact
median tie selects the lower concurrency. CPU and peak-process results are
retained and discussed; they cannot be omitted to make a candidate appear
better.

### 5.6 Checked-in decision and canonical budget proof

The raw concurrency report is written atomically to an ignored
`.superpowers/` path. A checked-in
`docs/performance/v2.1.1-concurrency-decision.md` records all four candidates,
all twelve samples, medians, stability evidence, CPU/process trade-offs, the
selection rule, and the selected explicit manifest value.

After the selected value is checked in, the canonical #84 full benchmark runs
`npm test` three times. Its report must pass the unchanged `90103 ms` budget.
The fast report must still pass `15000 ms`. The candidate report cannot replace
the canonical full report because only the latter proves the shipped package
command and checked-in configuration.

## 6. Data Flow

The semantic-test path is:

```text
manifest semantic owner
  -> public parser/dispatcher/orchestrator
  -> shared memory command store
  -> command result and state assertions
  -> boundary-inventory delegation check
  -> named real-store guarantee owners
```

The durable path is:

```text
manifest integration/e2e owner
  -> unique temporary root
  -> production artifact store or production CLI
  -> append/verify/lock/interruption/recovery assertion
  -> scoped cleanup
  -> no cross-root or temporary-state residue
```

The concurrency decision path is:

```text
validated manifest
  -> candidate worker for 1, 2, 3, 4
  -> three serial full-suite samples per candidate
  -> closed measurements and stability checks
  -> lowest stable median, lower-value tie break
  -> checked-in explicit concurrency
  -> canonical npm test capture
  -> unchanged full budget comparison
```

## 7. Failure Handling and Safety

Inventory validation fails before execution when ownership or delegation is
ambiguous. A memory-store mismatch is a correctness failure; it cannot be
excused as a performance trade-off. A production-store boundary failure keeps
its original error and cleanup cannot mask it.

A failed, signalled, incomplete, duplicated, reordered, leaking, or
isolation-unsafe concurrency sample makes its candidate ineligible. Failed
samples are retained in evidence and never contribute to a passing median. If
no candidate is stable, concurrency stays at `1` and the issue remains open.

If the fastest stable candidate fails the canonical `90103 ms` full budget,
the issue remains open for further in-scope reduction. The budget and baseline
remain unchanged, and the miss is not transferred to #88. No measurement may
run concurrently with another benchmark, package command, or correctness
suite.

## 8. Verification Strategy

Implementation follows test-driven development. Add failing tests before each
inventory, fixture, migration, isolation, benchmark-model, and scheduler
change. Correctness verification includes:

- closed inventory grammar, exact ownership, and manifest compatibility;
- memory/production semantic parity for shared store operations;
- retained production owners for every delegated real guarantee;
- repeated and concurrent root isolation with cleanup on success and failure;
- stable output order and exact child failure evidence at concurrency 1--4;
- every public lane, manifest integrity, `npm test`, and
  `npm pack --dry-run`; and
- byte comparison of the protected lock and performance baseline.

Before implementation changes, capture three clean `46c46b0` samples of the
focused design/project/feature command bundle. After migration, capture the
same three-sample bundle. Its median must improve by at least 30 percent and no
migrated owner may regress. The report retains the bundle wall time and each
owner's wall time for all three before and after samples. This threshold is
derived once as exactly 70 percent of the recorded pre-change median and is not
adjusted after results are known.

Then capture concurrency candidates 1--4, three full runs each, in isolation.
After checking in the winner, run one fresh full correctness suite and package
dry-run, followed by the canonical fast and full three-run captures and their
separate budget checks.

## 9. Acceptance and Completion

Issue #87 can move to Done only when all of the following are true:

1. the checked-in boundary inventory is closed, complete, sorted, and has
   exactly one primary owner per guarantee;
2. every semantic test moved to memory names all retained production-store
   guarantee owners it delegates;
3. atomicity, immutable bytes, lineage, verification, symlink safety, locking,
   interruption, resume, recovery, persisted idempotency, and packed execution
   still pass through production boundaries;
4. repeated and concurrent real-store tests prove unique roots, scoped
   cleanup, and zero cross-test state leakage;
5. the focused design/project/feature bundle improves by at least 30 percent
   with no migrated owner regression;
6. concurrency values 1, 2, 3, and 4 each have exactly three retained samples;
7. the checked-in concurrency is the stable candidate with the lowest median,
   with a lower-value tie break and complete CPU/process evidence;
8. manifest integrity, every public lane, `npm test`, and
   `npm pack --dry-run` pass;
9. the canonical fast three-run median remains at most `15000 ms`;
10. the canonical full three-run median is at most the unchanged `90103 ms`
    budget;
11. `package-lock.json` and `docs/performance/v2.1.1-baseline.json` are
    byte-identical to `46c46b0`; and
12. independent review finds no Critical or Important issue.

Failure of item 10 keeps #87 open and in progress. #88 performs the final
release audit; it does not inherit #87's unresolved performance debt.
