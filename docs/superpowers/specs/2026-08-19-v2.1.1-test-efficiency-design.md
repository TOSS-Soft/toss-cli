# TOSS CLI v2.1.1 Test Efficiency Design

**Status:** Approved for implementation planning

**Date:** 2026-08-19

**Release:** `@toss-software/cli@2.1.1`

**Epic:** [#83](https://github.com/TOSS-Soft/toss-cli/issues/83)
**Issues:** [#84](https://github.com/TOSS-Soft/toss-cli/issues/84),
[#85](https://github.com/TOSS-Soft/toss-cli/issues/85),
[#86](https://github.com/TOSS-Soft/toss-cli/issues/86),
[#87](https://github.com/TOSS-Soft/toss-cli/issues/87), and
[#88](https://github.com/TOSS-Soft/toss-cli/issues/88)

## 1. Purpose

Deliver TOSS CLI v2.1.1 as a patch release that shortens local and full-suite
test feedback without removing behavioral coverage or weakening any fail-closed
boundary. The release introduces explicit test ownership, reproducible
performance evidence, demand-driven validator initialization, a deliberate
boundary between semantic and durable-store tests, and measured bounded test
concurrency.

The release does not change the public TOSS CLI surface. Commands, options,
human and JSON output, exit codes, contracts, schemas, authority rules, state
machines, artifact durability, and recovery behavior remain compatible with
v2.1.0.

## 2. Current State and Baseline

The implementation starts from commit `4472175`, the `origin/main` commit tagged
as v2.1.0. At that revision, `package.json` and both package-lock roots identify
version 2.1.0.

The epic records this locked historical baseline on macOS and Node.js 26.6.0:

- `npm test`: 571 passing tests and 134.96 seconds wall time;
- final unscoped `node --test`: 127.15 seconds;
- `test/gate-cli-round1.test.js`: 32.76 seconds in isolation;
- `test/design-cli-runtime.test.js`: 41.97 seconds in isolation and about
  80 seconds under full-suite contention; and
- about 195.58 seconds user CPU and 302.84 seconds system CPU for the full run.

A fresh pre-change verification on the same macOS host and Node.js 26.6.0
passed with 603 tests and zero failures. Its final unscoped `node --test`
discovery took 126.28 seconds, rediscovered the named script tests, and treated
the `test/support` modules as standalone test inputs. The difference in test
counts is evidence that issue #84 must lock the exact inventory and measurement
protocol before accepting optimization results; it is not permission to adjust
the historical baseline after work begins.

## 3. Goals and Success Criteria

v2.1.1 is complete only when all of these conditions hold:

1. A documented local fast lane has a three-run median of at most 15 seconds on
   the named reference runner.
2. The full-suite three-run median is at least 30 percent faster than the locked
   same-runner baseline.
3. Every pre-v2.1.1 public behavior and failure boundary is mapped to one final
   owning test and lane.
4. Every intended script and `test/*.test.js` entry executes exactly once in the
   full suite; support modules are imports, not standalone test entries.
5. Test concurrency is explicit, bounded, deterministic, and selected from
   measurements of values 1 through 4.
6. Pull requests, `prepack`, and release validation continue to run the full
   correctness suite.
7. Package, lock, tag, npm, GitHub Packages, and GitHub Release metadata all
   identify exactly v2.1.1.

## 4. Scope and Non-Goals

### In scope

- reproducible performance measurement and versioned baseline evidence;
- explicit fast, integration, end-to-end, package, release, and full lanes;
- deterministic test selection and bounded scheduling;
- demand-driven, process-global immutable contract-validator caching;
- reducing redundant real-binary process composition while retaining its
  unique boundary coverage;
- moving purely semantic state-transition assertions to existing or equivalent
  in-memory service fixtures;
- retaining representative production artifact-store tests for every claimed
  durability, integrity, atomicity, and recovery guarantee; and
- v2.1.1 coverage audit, package preparation, release evidence, and publication.

### Out of scope

- TOSS Agent Runtime;
- new CLI commands, options, output formats, or exit codes;
- contract, schema, authority, state-machine, or persistence changes;
- a production option that disables validation, fsync, atomic replacement,
  lineage checks, or recovery;
- deleting an assertion without a behavior-to-test ownership mapping that
  demonstrates equivalent final coverage; and
- using timing assertions as ordinary correctness tests on shared runners.

## 5. Delivery Topology

Work uses one sequential pull request per issue. Each issue branch starts from
the latest verified `main` after the previous issue merges:

1. **#84 — Baseline and budgets.** Lock the inventory, measurement protocol,
   report schema, and reference-runner budgets.
2. **#85 — Explicit lanes.** Remove duplicate discovery and introduce the
   manifest and deterministic lane runner.
3. **#86 — Validator and process cost.** Use #84 evidence to reduce schema
   initialization and redundant subprocess composition.
4. **#87 — Store amplification and concurrency.** Move only semantic tests to
   memory, retain real durability boundaries, and select concurrency from
   measured values 1 through 4.
5. **#88 — Audit and release.** Independently reconcile behavior coverage,
   verify performance and correctness, prepare 2.1.1, and release after the
   final publication approval.

Although #85, #86, and #87 are conceptually independent after #84, they are
delivered sequentially. This keeps each performance delta attributable, avoids
stacked branch assumptions, and provides one review and rollback boundary per
optimization class.

## 6. Components

### 6.1 Versioned test inventory

A checked-in versioned inventory is the single source of truth for test entry
ownership. It assigns every intended executable entry to exactly one ownership
lane:

- **fast:** pure contracts, parsers, state transitions, and in-memory services;
- **integration:** artifact-store, filesystem, orchestration, recovery, and
  composed runtime services;
- **end-to-end:** real CLI process and environment boundaries;
- **package:** packed-artifact contents and execution;
- **release:** release metadata and workflow behavior.

**Full** is an aggregate command, not a second ownership lane. It runs the union
of every ownership lane plus any explicitly owned governance, documentation,
and reference-integrity entries exactly once.

The inventory uses repository-relative canonical paths and stable ordering.
Each executable entry has one owner. Files under `test/support`, fixtures, and
other imported helpers cannot be lane entries. A manifest-integrity check
compares the inventory against the repository and fails if an eligible entry is
missing, multiply owned, duplicated, unsafe, or unknown.

### 6.2 Deterministic lane runner

A cross-platform Node.js runner consumes the inventory without shell globs or
unbounded automatic discovery. It constructs explicit argument lists, runs
entries in stable order, uses one explicit bounded concurrency value, preserves
child output and exit status, and identifies the lane and entry that failed.

The package scripts expose at least `test:fast`, `test:integration`, `test:e2e`,
and `test:full`. `npm test` remains the canonical alias for the full correctness
suite, and `prepack` remains bound to that full path. Package and release checks
remain reachable through the full suite and may also have focused commands for
maintenance.

### 6.3 Benchmark and performance report

An opt-in benchmark command wraps the same lane runner used for correctness. It
runs three comparable iterations with warm installed dependencies and no
network access, then reports the median. The versioned JSON report contains:

- repository commit;
- Node.js version, platform, and architecture;
- dependency-lock SHA-256;
- command and selected lane;
- wall, user CPU, and system CPU time;
- exit status and peak fresh-process count;
- duplicate execution findings;
- ten slowest test files and named tests; and
- per-run values plus the calculated median.

Human-readable output is derived from the same normalized result. Ordinary
benchmark runs write to stdout or an ignored output location and do not mutate
tracked files. A baseline file changes only through an explicit baseline-update
option. The updater validates a successful three-run report and records the
exact environment and commit that produced it.

Correctness and performance budgets are separate. A slow shared runner cannot
make ordinary correctness tests fail. A dedicated budget check compares a
compatible report to the approved baseline and exits nonzero with stable
diagnostics for mismatched environments, invalid reports, failed iterations,
or regressions.

### 6.4 Contract-validator initialization

`src/contracts/validator.js` no longer loads and registers the entire schema
catalog merely because one schema is needed. Schema metadata is separated from
validator instances and organized into dependency-aware families. Validation
loads the requested schema and the exact referenced dependency closure, compiles
it once, and reuses an immutable process-global validator thereafter.

Issue #86 measures schema I/O, registration, compilation, first validation,
module loading, command execution, and process startup before selecting the
smallest safe implementation. Demand-driven compilation is the intended
default. Generated standalone validators remain an evaluated alternative, not
an assumption: they are adopted only if measurement shows a material advantage
without introducing generated-source drift or weakening validation behavior.

Valid and invalid fixture results, canonical JSON rejection, closed-schema
behavior, formats, references, unknown-schema handling, error classifications,
and normalized error content remain equivalent to v2.1.0.

### 6.5 CLI process boundary

Command-semantic matrices run in process through the public parser, dispatcher,
and lifecycle composition APIs when no operating-system process property is
under test. The minimum representative real-binary set continues to verify:

- argument parsing at the executable boundary;
- human stdout/stderr separation;
- JSON envelopes and stable exit codes;
- working-directory and environment isolation;
- no forbidden network access; and
- package executable behavior.

No command-specific assertion disappears when a redundant subprocess case is
removed; it moves to an in-process owner and remains listed in the coverage
inventory. Real-process cases continue to use the production executable.

### 6.6 Semantic and durable-store boundaries

Pure semantic assertions use the existing in-memory command-store pattern or a
focused equivalent. A semantic test may move away from disk only when its claim
does not include persistence, filesystem safety, durability, interruption, or
recovery.

A checked-in boundary inventory names the representative tests that continue to
use `createArtifactStore` for:

- atomic append and immutable revision bytes;
- monotonic revision and exact parent lineage;
- content hashes and exact-reference verification;
- path containment and symbolic-link rejection;
- append-lock behavior and concurrent writers;
- interrupted temporary-file recovery and resumable workflows;
- idempotent reruns and partial-operation recovery; and
- execution from the packed production artifact.

Every semantic test moved to memory retains an explicit real-store counterpart
for the production boundary it no longer exercises. Tests use isolated temporary
roots and cannot observe, overwrite, or clean another test's state.

### 6.7 Bounded concurrency

Issue #87 benchmarks full-suite concurrency values 1, 2, 3, and 4 through the
#84 protocol. The selected default is the value with the lowest stable median
that produces zero correctness failures or isolation flakes. The decision also
considers user CPU, system CPU, and peak fresh-process count; it is never derived
from ambient CPU count. The chosen value is explicit and versioned with the
runner configuration.

## 7. Data Flow

The correctness path is:

```text
package script
  -> manifest integrity validation
  -> requested lane selection
  -> stable explicit entry list
  -> bounded runner
  -> entry outputs and exit statuses
  -> normalized lane result
```

The performance path is:

```text
benchmark command
  -> same manifest and lane runner
  -> three compatible runs
  -> normalized measurements
  -> median and slow-entry analysis
  -> human output + versioned JSON
  -> optional separate budget comparison
```

The validator path is:

```text
schema ID
  -> registry lookup
  -> exact dependency closure
  -> load and compile on first use
  -> immutable process-global cache
  -> canonicalize and validate document
  -> unchanged normalized result
```

## 8. Failure Handling and Safety

The test runner fails closed before execution if inventory ownership is invalid.
Diagnostics identify the exact path, conflicting lanes, unsafe path, or missing
owner. A child test failure preserves its nonzero exit and cannot be converted
to a passing aggregate.

The benchmark refuses to compare reports from incompatible environments or
dependency locks. A failed iteration cannot contribute a successful median. An
ordinary measurement never updates the baseline implicitly.

If a performance target is missed, the issue remains open. The implementation
must improve the relevant cost or revise the design with explicit approval; it
must not remove coverage, weaken a real boundary, increase concurrency without
evidence, or relax a budget after seeing the result.

Validator loading fails closed for unknown schemas, unresolved dependencies,
invalid schema definitions, and compile failures. Callers cannot mutate the
registry, cached Ajv instance, or compiled validator.

Store optimizations do not add test-only switches to production durability.
Atomic replacement, validation, lineage, symlink defense, lock behavior, and
recovery remain production code paths exercised by their boundary tests.

## 9. Verification Strategy

Each issue follows test-driven development and provides focused tests for its
new tooling or refactoring. Before each pull request is considered ready, it
runs:

1. the issue-focused lane and failure-path tests;
2. manifest-integrity validation;
3. the complete `npm test` correctness suite;
4. applicable package, governance, documentation, and reference checks; and
5. the issue-specific three-run benchmark when performance is claimed.

The named macOS/Node.js 26.6.0 host supplies acceptance performance evidence.
GitHub Actions on Node.js 24 independently verifies correctness and the package;
shared Actions timing is informative and does not replace the reference-runner
budget decision.

Issue #88 reconciles a behavior-to-test coverage inventory against v2.1.0,
proves that each executable entry has one lane, and runs the final three-run
fast and full benchmarks. It also runs `npm test`, `npm pack --dry-run`, packed
artifact execution, governance, reference-integrity, documentation, release
workflow, and supported Node-version checks.

## 10. Release Process and Final Authority Gate

Issue #88 updates `package.json`, `package-lock.json`, and both root lockfile
version fields to exactly 2.1.1 and adds v2.1.1 release notes and
release-specific tests. Release
notes describe the benchmark environment and measured contributor-workflow
improvements without making unsupported product-runtime claims.

The release candidate is merged to `main` only after every child issue and all
correctness and performance gates pass. The exact merged-main commit is verified
again before tagging. A final user approval is required before the `v2.1.1` tag
is created or pushed.

After that approval, the existing tag-triggered workflow must:

1. verify that the exact tag, package version, checked-out commit, and `main`
   ancestry agree;
2. run the full correctness suite;
3. build and verify one npm tarball;
4. publish `@toss-software/cli@2.1.1` to npm with provenance;
5. publish the corresponding `@toss-soft/cli@2.1.1` GitHub Package; and
6. create a non-draft, non-prerelease latest GitHub Release with the verified
   tarball.

Release evidence records the commit, workflow runs, benchmark report, package
digest, npm version, and GitHub Release URL. Epic #83 and the v2.1.1 milestone
close only after all published surfaces are independently verified.

## 12. Approved Decisions

- The release is TOSS CLI-only and changes no public behavior.
- Delivery is sequential and uses one independent pull request per issue.
- Measurement is established before optimization.
- Test selection is explicit, versioned, and cross-platform.
- Demand-driven validator compilation is the intended implementation, subject
  to issue #86's measured alternative comparison.
- Semantic tests may use memory only when a named real-store test retains the
  production boundary claim.
- Concurrency is selected from measured values 1 through 4.
- Performance budgets are separate from ordinary correctness tests.
- External publication requires a final user approval after all gates pass.
