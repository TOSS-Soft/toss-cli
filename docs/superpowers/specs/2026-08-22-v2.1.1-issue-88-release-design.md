# TOSS CLI v2.1.1 Issue #88 Coverage Audit and Release Design

**Date:** 2026-08-22
**Issue:** #88
**Epic:** #83
**Release:** `@toss-software/cli@2.1.1`
**Base:** `039b5f7d63244741be26263a69fc74e2fd7ed499`

## 1. Goal

Independently prove that the v2.1.1 test-efficiency stack preserves the public
and fail-closed behavior of v2.1.0, meets both locked performance targets, and
can publish one exact `2.1.1` artifact through the existing tag-triggered
release workflow.

The work has two authority gates. The release-candidate gate prepares and
reviews the complete change without merging or publishing. The publication
gate begins only after the issue stack is merged to `main`, the merged commit is
verified again, and the user explicitly approves creation and push of the
`v2.1.1` tag.

## 2. Fixed Inputs and Constraints

- The pre-release behavior source is annotated tag `v2.1.0`, resolving to
  commit `4472175eac91275cafab2993f68722febdb9eb59`.
- The release-candidate branch starts at the final #87 commit
  `039b5f7d63244741be26263a69fc74e2fd7ed499`.
- TOSS Agent Runtime is outside this release.
- No public CLI command, option, output, exit code, schema, contract,
  authority, state-machine, durability, recovery, or filesystem-security
  behavior may change.
- The Node.js engine declaration remains `>=20`.
- Pull requests, `prepack`, and release validation keep the canonical full
  suite. Performance budgets remain separate from correctness tests.
- The locked fast and full limits remain `15000 ms` and `90103 ms`.
- `docs/performance/v2.1.1-baseline.json` is immutable during #88.
- Publication continues through GitHub Actions Trusted Publishing/OIDC. No npm
  token or other long-lived publishing credential is introduced.
- No merge, tag, npm publication, GitHub Package, or GitHub Release is created
  during release-candidate preparation.

## 3. Delivery Architecture

### 3.1 Release-candidate phase

Branch `agent/issue-88-v2.1.1-release` is stacked on #87. It contains the
coverage audit, exact `2.1.1` metadata, release notes, compatibility checks,
release-evidence tooling, and release-specific tests. Its pull request targets
`agent/issue-87-durable-store-concurrency` and remains draft until independent
review and every local release-candidate gate pass.

### 3.2 Integration phase

The prepared pull-request stack is integrated only after explicit user
approval. The issue branches are merged in dependency order, retargeting each
successor to `main` after its predecessor lands:

1. #93 / #85 and its inherited #84 baseline work;
2. #94 / #86;
3. #95 / #87; and
4. the #88 release-candidate pull request.

Each merge must be observed on `main` before the next branch is retargeted or
merged. A conflict, failing required check, or unexpected diff stops the chain.

### 3.3 Publication phase

The exact merged-main commit is checked out cleanly and all final release gates
are rerun. The controller then reports the commit, version, tarball name and
SHA-256, benchmark medians, and external actions that the tag will trigger.
Only a separate explicit user approval authorizes creation and push of the
annotated `v2.1.1` tag.

The tag-triggered workflow validates ancestry and metadata, tests the release,
builds one canonical npm tarball, publishes it to npm, derives and publishes
the GitHub Packages variant, creates the GitHub Release, and attaches the
canonical tarball and machine-readable release evidence.

## 4. Coverage Audit

`docs/testing/v2.1.1-coverage-audit.json` is a closed audit record, not an
execution manifest. `scripts/test-manifest.json` remains the sole current test
owner and lane source of truth.

The audit root contains:

- schema version;
- exact v2.1.0 tag and source commit;
- one ASCII-sorted row for every executable test or check entry present at
  v2.1.0; and
- the final owner, final lane, disposition, and retained evidence for each row.

Allowed dispositions are `unchanged`, `moved`, `coalesced`, and `replaced`.
`moved`, `coalesced`, and `replaced` rows must name the final behavioral test
or boundary guarantee that preserves the original claim. A row cannot use its
own assertion as evidence.

`scripts/coverage-audit.mjs` validates the checked-in audit against two inputs:

1. a locked discovery of executable v2.1.0 entries from the tag tree; and
2. the normalized final manifest and boundary inventory.

It fails closed for an unknown field, unsafe path, wrong source commit, missing
or duplicate legacy entry, missing final owner, incorrect final lane,
unrecognized disposition, absent preservation evidence, duplicate mapping, or
inventory drift. It never executes tests and never influences lane selection.

`test/coverage-audit.test.js` covers the closed schema, tag identity,
one-to-one legacy inventory, manifest-derived ownership, every failure class,
and the checked-in audit. The manifest owns this test in the release lane.

## 5. Version and Release Notes

Release-candidate metadata changes exactly these version fields to `2.1.1`:

- `package.json.version`;
- `package-lock.json.version`; and
- `package-lock.json.packages[""].version`.

No tag is created by the version-update commit. The release notes live at
`docs/releases/v2.1.1.md` and contain only:

- explicit and deterministic test lanes;
- contributor fast-feedback improvements;
- internal contract-validator cold-start reduction;
- durable-test amplification reduction and bounded concurrency;
- compatibility and safety guarantees;
- benchmark environment and measured fast/full medians; and
- verification and closed-issue inventory for #84 through #88.

The notes must not claim that the public CLI or user workloads run faster.
They must state that behavior, engine floor, contracts, durability, and release
authority are unchanged.

The v2.1.0 release contract is replaced by
`test/release-v2.1.1.test.js`. It locks exact package/lock versions, note
headings and permitted claims, legacy CLI entry points, coverage-audit
completeness, release-lane ownership, and the continued full/prepack gates.

## 6. Supported Node Versions

The CI correctness job uses an explicit matrix of Node.js `20` and `24`.
Each matrix member installs from the package lock, runs `npm test`, and runs
`npm pack --dry-run`. Node 20 proves the declared floor; Node 24 matches the
release workflow runtime. The tag-triggered publisher stays on Node 24 so the
publication environment does not change during the patch release.

Local preparation must run the release-focused contracts under the available
reference runtime and exercise an actual Node 20 binary before the candidate is
declared ready. GitHub CI on the main-targeted release PR and merged main is the
authoritative cross-platform Node 20/24 result.

## 7. Release Notes and Evidence in the Workflow

The publish workflow must use `docs/releases/v2.1.1.md` through the versioned
path `docs/releases/v${VERSION}.md`; generated Git history is not the release
body. `scripts/release-metadata.mjs` validates that the versioned notes file
exists and exposes its path with the version and artifact name.

The release tag must be annotated. Its message uses a closed
`toss-release-tag.v1` JSON object containing the exact merged-main commit, the
canonical final fast/full report SHA-256 values, their medians, and their
limits. `scripts/release-metadata.mjs` rejects a lightweight tag, unknown tag
message fields, mismatched commit, malformed hash, or failed budget claim, and
passes the validated benchmark identity into the release evidence. This binds
the reference-host measurements to the immutable tag without committing raw
host reports or creating a post-measurement commit.

`scripts/release-evidence.mjs` creates and validates a closed JSON record with:

- schema version;
- exact tag, version, and release commit;
- final fast/full report SHA-256 values, medians, and locked limits from the
  validated annotated tag;
- canonical npm tarball filename and SHA-256;
- GitHub workflow repository, run ID, and run URL;
- verified npm and GitHub Packages identities; and
- GitHub Release tag, URL, draft/prerelease flags, and attached asset names.

The workflow does not trust caller-supplied digests or package identities. It
derives the tarball digest from the validated artifact, derives commit/tag data
from GitHub and Git, and records package identities only after the publishing
jobs verify them. The final job validates the evidence and uploads both the
tarball and `release-evidence.json` to the non-draft, non-prerelease release.

`scripts/release-workflow-test.js` uses local fake publishers and GitHub clients
to prove permissions, artifact flow, exact notes usage, idempotent publication,
evidence construction, and failure behavior without network mutation.

## 8. Performance Evidence

The named reference host is macOS with the same dependency state and benchmark
runner used for the locked baseline. Performance commands run serially and
retain raw reports outside Git tracking.

The release candidate requires:

- three successful fast samples with median at most `15000 ms`; and
- three successful full samples with median at most `90103 ms`, which is at
  least 30% faster than the locked baseline.

Every retained sample must have successful exit status, complete process
evidence, the exact candidate commit identity, and no duplicate test entry.
Missing, failed, mixed-identity, malformed, or noncanonical evidence stops the
release. A budget miss never triggers an automatic recapture.

The exact benchmark reports and SHA-256 values are recorded in the #88 task
handoff and pull-request body. The release notes include the environment,
sample values, median, and limits but not ignored local paths.

## 9. Verification Order

Release-candidate verification is serial:

1. coverage-audit, test-manifest, and boundary integrity;
2. release, coverage, workflow, governance, reference, documentation, and
   performance-tool focused tests;
3. fast, integration, end-to-end, package, release, and full lane ownership;
4. Node 20 and Node 24 correctness/package checks;
5. canonical `npm test`;
6. `npm pack --dry-run` and one packed-artifact install/CLI smoke check;
7. fast three-run capture and budget;
8. full three-run capture and budget;
9. protected baseline checks, whitespace checks, clean index/worktree; and
10. independent spec and code review with no open Critical, Important, or
    Minor findings.

After all issue branches merge, the same sequence is rerun on exact merged
main. Existing final benchmark evidence may not be relabeled with the merged
commit; fresh merged-main captures are required.

## 10. Failure and Recovery Rules

- Any failed gate stops before the next merge, tag, or publication boundary.
- A failed stack merge leaves later pull requests untouched. No force push or
  history rewrite is used without explicit user approval.
- A failed merged-main verification leaves `main` untagged and reports the
  exact failure.
- A tag is never moved, replaced, or deleted automatically.
- If the tag workflow partially succeeds, the controller records which
  registries or release surfaces changed and does not manually republish or
  conceal the partial state.
- Idempotent workflow paths may verify an already-published exact version, but
  they may not replace a different artifact under the same version.
- #88, #83, and the v2.1.1 milestone remain open until every external surface
  is independently verified.

## 11. Authority Gates

Four decisions remain distinct:

1. this design approval authorizes release-candidate implementation only;
2. a later integration approval authorizes merging the prepared PR stack;
3. a separate final publication approval authorizes creation and push of the
   annotated `v2.1.1` tag; and
4. successful workflow completion authorizes closing #88, #83, and the
   v2.1.1 milestone only after independent verification.

No earlier approval implies a later one.

## 12. Acceptance Criteria

- The coverage audit maps every v2.1.0 executable test/check entry to one valid
  final owner and lane with explicit preservation evidence.
- No missing, duplicate, unowned, or multiply owned eligible test entry exists.
- Node 20 and Node 24 correctness/package checks pass without changing the
  `>=20` engine floor.
- Fast and full three-run medians pass `15000 ms` and `90103 ms` respectively.
- `npm test`, every public lane, `npm pack --dry-run`, packed-artifact smoke,
  governance, reference-integrity, documentation, and release workflow checks
  pass.
- Package and both lock roots equal exactly `2.1.1`.
- Release notes make no unsupported product-runtime claim and name the
  benchmark environment and values.
- The exact verified merged-main commit receives annotated tag `v2.1.1` only
  after explicit user approval.
- npm exposes `@toss-software/cli@2.1.1`; GitHub Packages exposes
  `@toss-soft/cli@2.1.1`; and GitHub exposes a non-draft, non-prerelease latest
  v2.1.1 release with the canonical tarball and validated evidence asset.
- Release evidence records commit, workflow run, benchmark report hashes,
  package digest, both package identities, and Release URL.
- #88, #83, and milestone v2.1.1 close only after all checks succeed.

## 13. Non-Goals

- Changing any product command, contract, generated output, or persistence
  behavior.
- Raising the Node.js engine floor.
- Relaxing the locked performance budgets or refreshing the baseline.
- Replacing Trusted Publishing with manual credentials.
- Publishing from a feature branch or before the exact merged-main verification
  and final tag approval.
- Refactoring unrelated test or release infrastructure.
