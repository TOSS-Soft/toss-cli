# TOSS CLI v2.1.0 Agent Pipeline Design

**Date:** 2026-08-17

**Status:** Approved for planning

## Goal

Deliver every open issue from #12 through #32 as TOSS CLI v2.1.0. The
release adds a model-independent PM → Architect → PM Finalization → Spec
Auditor pipeline, immutable and traceable artifacts, fail-closed readiness
gates, a user-facing lifecycle command surface, and a risk-based UI/UX design
pipeline.

Each issue receives its own branch and pull request. A pull request must pass
the required `test` status check and merge to `main` before work starts on the
next dependent issue. Issue #24 is the final release/epic pull request.

## Current State and Required Baseline Repair

The current release is v2.0.0. The repository is a Node.js ESM CLI with Node
20 as the published engine floor, Node 24 in CI, `yaml` as its only runtime
dependency, a 961-line command module, and script-based tests.

The existing test chain fails on macOS because `node:os.tmpdir()` yields a
lexical `/var/...` path while a child shell canonicalizes its working directory
to `/private/var/...`. The release workflow test compares those equivalent
paths as unequal strings. Before issue #12, a new regression issue is created
and completed in its own pull request. The repair must compare canonical paths
while preserving the test's requirement that publication receives an absolute
tarball path.

## Architecture and Module Boundaries

The current `src/cli.js` remains the process entry point during migration, but
new behavior is placed in focused modules:

- `src/contracts/` loads versioned schemas, performs JSON Schema validation,
  and runs cross-document semantic validation.
- `src/artifacts/` canonicalizes JSON, calculates integrity hashes, writes and
  discovers revisions, and maintains reconstructable indexes.
- `src/pipeline/` owns analysis artifacts, ambiguity decisions, architecture,
  issue planning, audit, traceability, state transitions, readiness, and design
  orchestration.
- `src/commands/` owns command definitions and delegates domain work without
  containing validation or persistence rules.
- `src/output/` renders stable machine envelopes and readable terminal views.
- `contracts/` contains published JSON Schema documents organized into
  `common`, `agents`, `pipeline`, and `design` packages.
- `test/fixtures/` contains deterministic valid, invalid, stale, corrupt,
  interrupted, and gated workflow fixtures.

The repository adds Ajv with JSON Schema 2020-12 support as the contract
validator. YAML remains the input and human-projection library. Domain modules
do not depend on terminal formatting, child processes, or GitHub access.

## Agent Contract Protocol v1

Canonical artifacts are JSON. YAML is an input format and a lossless human
projection; it is never the integrity source. Every artifact uses an immutable
envelope containing:

- `schema_version` and `document_type`;
- globally unique `artifact_id` and monotonic `revision`;
- `run_id`, producer identity, model/runtime identity when applicable, and
  timestamps;
- source revision/hash and provenance locations;
- parent and input artifact revision references;
- canonical content SHA-256.

Entity identifiers use the prefixes required by #12: `REQ`, `NFR`, `BR`,
`FLOW`, `ARCHQ`, `ADR`, `EPIC`, `ISSUE`, `AC`, `RISK`, `ASM`, and `Q`.
Schema validation checks document shape and prefix syntax. Semantic validation
checks duplicate meanings, dangling references, invalid mutations, cycles,
coverage, stale revisions, and role boundaries.

Unknown schema versions, content hash mismatches, missing inputs, and invalid
role mutations fail closed. The PM owns product requirements and business
rules, the Architect owns technical decisions, and the Spec/Design Auditors
only emit findings.

## Immutable Artifact Store

Generated projects keep canonical machine artifacts under
`project-management/artifacts/`. A revision is stored beneath its document type
and artifact identity with its revision number and content hash in the file
name. Existing revision files are never overwritten.

Writes use a same-directory temporary file, file synchronization, and atomic
rename. A revision becomes discoverable only after its full payload and hash
have been verified. Mutable indexes are derived caches and can be rebuilt from
immutable revisions. Interrupted temporary files are ignored or recovered
without becoming valid artifacts.

Appending an identical command result is idempotent: the store returns the
existing matching revision instead of creating a duplicate. Parent/input
references must resolve to exact verified revisions before a write is
committed. Source changes mark downstream artifacts stale without deleting
their historical revisions.

## Provider-Neutral Pipeline and Data Flow

v2.1.0 does not embed a model vendor, API key, or network model call. Agent
stages consume structured interactive answers or `--from` JSON/YAML input and
produce provider-neutral ACP artifacts. A future provider adapter can supply
the same contracts without changing persistence, gates, or commands.

The project pipeline is:

```text
project source
→ pm-analysis.v1
→ decision-package.v1 when required
→ architecture.v1 + adr.v1
→ issue-plan.v1
→ spec-audit.v1
→ traceability graph
→ PDoR result
→ read-only GitHub issue preview
→ explicit gated publish
```

The state machine permits only declared transitions among `ANALYZING`,
`QUESTIONS_PENDING`, `USER_DECISION`, `ARCHITECTURE_PENDING`,
`ADR_PENDING_APPROVAL`, `PM_FINALIZATION`, `SPEC_AUDIT`, and
`READY_FOR_ISSUES`, plus explicit failed/blocked recovery states. Resume starts
from the last verified immutable revision. Every transition is an auditable
event artifact.

Feature preparation creates delta artifacts linked to the current project
revision; it never silently rewrites full project history.

## Ambiguity, Audit, and Readiness Gates

The existing A1/A2/A3 authority model is mapped normatively to P0–P4 severity.
Unresolved P0–P2 questions block progress. P3/P4 assumptions may proceed only
with provenance, impact, and reversibility.

Spec Auditor findings contain severity, type, owner, evidence, and affected
entities. The auditor cannot mutate its inputs. Requirement coverage,
acceptance-criteria coverage, ADR consistency, orphan detection, duplicates,
dangling references, and dependency cycles are deterministic checks.

PDoR returns a versioned JSON result with evidence per failed rule. It reports
warnings separately and sets `ready_for_issue_generation=true` only when every
blocking project gate passes for the current source revision.

## CLI Contract

The command families are:

```text
toss project <create|analyze|prepare|status|resume>
toss feature <add|analyze|prepare|status>
toss decisions <list|answer>
toss architecture <review|approve>
toss plan show
toss audit run
toss readiness check
toss issues <preview|publish>
toss trace <ENTITY-ID>
toss artifacts <list|inspect>
toss validate <FILE>
toss design <init|analyze|prepare|status|flows|wireframes|direction|system|screens|prototype|audit|review|approve>
```

Common behavior supports `--from`, `--non-interactive`, `--json`, `--continue`,
and `--project`. JSON output uses a stable versioned command-result envelope.
Human output goes to stdout, actionable errors go to stderr, and invalid input,
blocked decisions, failed gates, or illegal transitions return documented
non-zero exit codes.

The existing `toss init`, `toss create`, and fast scaffold commands remain
available in v2.1.0. Help and README text identify their relationship to the
new lifecycle commands without removing established behavior.

## GitHub Issue Publication

`toss issues preview` is always read-only. `toss issues publish` is dry-run by
default. Real mutation requires `--apply`, exact authority provenance, current
source revisions, state `READY_FOR_ISSUES`, Spec Audit PASS, PDoR PASS, and any
required design approval.

Published issue bodies contain immutable local entity markers, requirements,
ADRs, dependencies, and acceptance criteria. The writer discovers existing
markers before creating issues, persists local-to-GitHub mappings as result
artifacts, and resumes only missing work after partial failure. API,
authentication, permission, and rate-limit errors do not advance readiness.

GitHub access is isolated behind an adapter and uses the authenticated `gh`
CLI already required for repository operations. Tests use fakes and never
mutate GitHub.

## UI/UX Design Pipeline

Versioned design contracts extend ACP without changing its envelope or
immutability rules. Repository artifacts are canonical for intent, rules,
revision, approval, and traceability. Figma, Pencil, and code-native production
assets are referenced through manifests with tool, URI/file identity, version,
and integrity metadata.

The PM classifies UI impact as `LITE`, `STANDARD`, `CRITICAL`, or
`NOT_APPLICABLE`. Critical work cannot be silently downgraded. Verified company
design-system rules remain binding; project extensions and exceptions require
explicit scoped approval.

Design Auditor is read-only and checks flows, screen states, component
consistency, responsive behavior, accessibility, company-system violations,
and level-specific evidence. UI Design DoR is separate from project PDoR, but
both must pass before UI-affecting issues can be published. Approval binds to
the exact design artifact graph revision and becomes stale when any upstream
revision changes.

## Error Handling and Safety

- All unknown versions, invalid references, corrupt artifacts, illegal state
  transitions, stale approvals, and unmet publish gates fail closed.
- Read-only preview and validation commands never write GitHub state.
- No artifact revision is overwritten or deleted during normal operation.
- Filesystem writes reject symlink escapes and reuse the repository's existing
  containment protections.
- Secrets and tokens are never accepted as command-line values or persisted in
  artifacts.
- Machine output remains valid JSON on failure and contains finding IDs,
  evidence, blocking owner, and the next permitted action.

## Test Strategy

Every issue pull request follows test-driven development:

1. add the smallest automated test that fails for the issue's acceptance
   criterion;
2. confirm the expected failure;
3. implement the minimal contract or behavior;
4. run the focused test and full suite;
5. run package and diff integrity checks;
6. open a pull request containing `Closes #N`;
7. wait for required CI and merge before starting the next issue.

Tests use Node's built-in test runner, deterministic JSON/YAML fixtures, fake
clocks/IDs where necessary, temporary repositories, and fake GitHub adapters.
Coverage includes valid/invalid schemas, duplicate IDs, dangling references,
hash corruption, interrupted writes, idempotency, cycles, stale revisions,
role violations, every state transition, blocked decisions, PDoR/Design DoR
matrices, CLI human/JSON output, dry-run/apply boundaries, partial GitHub
failure, resume, README/help drift, package contents, and the existing release
workflow.

## Pull Request and Release Process

Each issue uses a dedicated branch and pull request. The branch starts from the
latest merged `main`; it does not stack unmerged dependencies. Each PR is
reviewed against the issue acceptance criteria and merged only after the strict
`test` status check succeeds. The issue closes through the PR body.

After #12–#23 and #25–#32 are merged, #24 receives the final epic pull request.
That PR verifies the backlog, adds release-facing documentation where needed,
sets `package.json` and `package-lock.json` to `2.1.0`, and runs the complete
test/package chain. After #24 merges and merged-main CI succeeds, tag `v2.1.0`
is created at that exact main commit and pushed.

The existing tag workflow validates main ancestry and version equality,
publishes the verified tarball to npm as `@toss-software/cli@2.1.0`, derives
and publishes `@toss-soft/cli@2.1.0` to GitHub Packages, and creates the latest
non-draft GitHub Release with the canonical tarball. Completion requires all
jobs to succeed and the release/package versions to be independently verified.

## Out of Scope

- Embedding or selecting a model provider.
- Storing model API keys or production credentials.
- Replacing the existing fast scaffold commands in v2.1.0.
- A graphical application for managing the pipeline.
- Automatically publishing issues without explicit `--apply` and passing
  gates.
- Automatically migrating or rewriting populated projects from older
  governance layouts.

## Completion Criteria

The initiative is complete only when:

- every acceptance criterion in #12–#23 and #25–#32 is covered by automated
  tests and merged through its own pull request;
- #24's backlog is complete and the epic is closed by its own release PR;
- all repository tests, package checks, schema fixtures, CLI workflows, and
  release-workflow tests pass on the final main commit;
- no open issue from the approved scope remains;
- npm, GitHub Packages, and GitHub Release all expose version 2.1.0 from the
  same verified source commit.
